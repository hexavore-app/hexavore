# 05 — Intelligence artificielle

L'IA a **un seul rôle** dans cette application : transformer une photo ou une phrase en une liste d'aliments avec leurs quantités. Elle ne calcule pas les macros — c'est [04](04-sources-de-donnees.md#résolution--du-texte-de-lia-à-un-aliment) qui s'en charge, à partir de bases traçables.

Ce découpage est la décision la plus structurante du document. Il donne des résultats reproductibles (deux analyses de la même assiette donnent les mêmes calories), sourçables (chaque ligne indique d'où vient son chiffre), et moins coûteux (une sortie de 200 tokens au lieu de 800).

---

## Le contrat

Une interface, deux entrées possibles, une sortie. Tout le reste de l'application ne connaît que ça.

```kotlin
/**
 * Extrait une liste d'aliments consommés à partir d'une photo ou d'une description.
 * Ne produit aucune valeur nutritionnelle : voir NutritionResolver.
 */
fun interface FoodRecognizer {
    suspend fun recognize(input: RecognitionInput): RecognitionOutcome
}

sealed interface RecognitionInput {
    /** @param note précision libre de l'utilisateur, ex. « l'assiette fait 24 cm ». */
    class Photo(val jpeg: ByteArray, val note: String?) : RecognitionInput
    data class Text(val description: String) : RecognitionInput
}

sealed interface RecognitionOutcome {
    data class Recognized(val recognition: Recognition) : RecognitionOutcome
    data class Failed(val error: AiError) : RecognitionOutcome
}

data class Recognition(
    val items: List<RecognizedItem>,
    val usage: TokenUsage?,
)

data class RecognizedItem(
    val label: String,          // « jus d'orange »
    val quantity: Double,       // 200.0
    val unit: EstimatedUnit,    // ML
    val confidence: Float,      // 0f..1f, tel que rendu par le modèle
)

enum class EstimatedUnit { G, ML, PIECE, SLICE, TBSP, TSP, BOWL, PLATE, GLASS }
```

Photo et texte partagent le même contrat, donc le même pipeline, le même écran de validation, les mêmes tests. Ajouter un troisième mode d'entrée (dictée vocale, par exemple) revient à ajouter une variante de `RecognitionInput` — sans toucher au reste.

**Trois écarts avec la première rédaction de ce document**, tous tranchés en [D72](11-decisions.md#d72--le-contrat-de-reconnaissance-et-un-parseur-qui-ne-croit-pas-le-modèle-sur-parole---validée) :

- **`EstimatedUnit` et non `QuantityUnit`.** Le journal a déjà un `QuantityUnit`, qui porte un poids en grammes ([D42](11-decisions.md)). Celui du modèle n'en porte aucun — « un bol » ne pèse rien tant que le résolveur n'a pas décidé ce que pèse un bol. Ce sont deux choses, et la conversion de l'une vers l'autre est le travail de [04](04-sources-de-donnees.md#conversion-des-quantités).
- **`RecognitionOutcome` et non `Result`.** `kotlin.Result` exige une `Throwable` en échec, ce qui ferait d'`AiError` une exception. Or ces issues sont attendues, et [06](06-architecture.md) interdit qu'un port en lève une — c'est la forme de `ProductLookup`.
- **`Photo` n'est pas une `data class`.** Une `data class` qui porte un `ByteArray` fabrique une égalité fausse : elle compare les références du tableau.

## Fournisseurs

Six implémentations de `FoodRecognizer`, chacune dans sa classe, sélectionnées à l'exécution par un `FoodRecognizerFactory` à partir des réglages.

| Fournisseur | Endpoint | Sortie structurée | Vision |
|---|---|---|---|
| Google Gemini | `generativelanguage.googleapis.com/v1beta` | `responseMimeType` + `responseSchema` | oui |
| OpenAI | `api.openai.com/v1` | `response_format: json_schema` | oui |
| Anthropic | `api.anthropic.com/v1` | `output_config.format` (schéma JSON) | oui |
| DeepSeek | `api.deepseek.com/v1` | `response_format: json_object` | selon modèle |
| Mistral | `api.mistral.ai/v1` | `response_format: json_object` | selon modèle |
| **OpenAI-compatible** | **URL libre** | `json_object` | selon modèle |

Le dernier n'est pas un bouche-trou, c'est l'assurance-vie du projet : une URL de base et un nom de modèle suffisent à brancher OpenRouter, Groq, un Ollama sur le réseau local, LM Studio, ou n'importe quel fournisseur qui n'existe pas encore.

Un modèle sans capacité vision est accepté pour le mode texte et signalé comme indisponible pour le mode photo — testé au moment de l'enregistrement de la clé, pas au moment où l'utilisateur veut s'en servir.

### Ajouter un fournisseur

C'est le test d'ouverture-fermeture du projet, et il doit rester à ce prix :

1. une classe implémentant `ProviderRecognizer` ;
2. une entrée dans l'énumération `AiProvider` (nom affiché, URL par défaut, modèles suggérés, capacité vision) ;
3. une branche dans le `when` de la fabrique.

**La troisième étape est un `when` et non une liaison Hilt**, et c'est un renforcement plutôt qu'un relâchement : une carte de liaisons oubliée plante à l'exécution, sur l'appareil de quelqu'un, alors qu'une branche manquante **ne compile pas**. La vérification d'exhaustivité de Kotlin fait gratuitement le travail qu'une carte demanderait de se rappeler ([D76](11-decisions.md#d76--trois-prescriptions-de-docs05-tombent-au-contact-de-lapi-et-le-raisonnement-reste-actif---validée)).

`ProviderRecognizer` et non `FoodRecognizer` : le second est le port du domaine, qui ne parle pas de clés d'API et ne doit pas commencer. Le premier prend la configuration en paramètre, parce qu'elle change quand l'utilisateur corrige sa clé alors que l'objet, lui, vit aussi longtemps que l'application.

Aucun `when` **ailleurs** dans le code, aucun écran à modifier, aucun test existant à retoucher. Si une quatrième étape apparaît, c'est que l'abstraction a fui — il faut la corriger, pas contourner.

## Prompt

Versionné dans `assets/prompts/extract_fr_v2.txt`, chargé au démarrage, jamais construit par concaténation dispersée dans le code. La version utilisée est enregistrée avec chaque analyse : sans ça, impossible de comprendre plus tard pourquoi une extraction s'est mal passée.

**~~Deux~~ Trois prompts, trois versions.** `extract_fr_v2.txt` pose la reconnaissance, `estimate_fr_v2.txt` l'estimation de l'étape 4 de [04](04-sources-de-donnees.md), et `deep_fr_v2.txt` décrit les deux outils de l'analyse approfondie. Les deux premiers sont passés en `v2` quand chaque ligne a gagné son **poids en grammes** ([D112](11-decisions.md#d112--le-modèle-pèse-ce-quil-compte-parce-quune-pièce-ne-dit-rien-de-sa-taille---validée)) : un prompt qui demande autre chose n'est plus le même, et c'est précisément ce que la version enregistrée avec chaque analyse sert à retrouver. Un compteur unique aurait renuméroté l'un en corrigeant l'autre, et annoncé un changement là où il n'y en avait pas ([D98](11-decisions.md#d98--le-modèle-doit-se-prononcer-sur-les-six-valeurs-et--inconnu--sécrit---validée)).

**Le poids d'une ligne reconnue suit la même règle** : exigé, et autorisé à valoir `null` ([D112](11-decisions.md#d112--le-modèle-pèse-ce-quil-compte-parce-quune-pièce-ne-dit-rien-de-sa-taille---validée)). Un champ facultatif serait un champ jamais rempli, et cinq cacahuètes repèseraient cinq cents grammes.

**Le schéma d'estimation exige les six valeurs, et chacune peut valoir `null`.** Ne rendre obligatoire que le libellé — pour qu'un modèle puisse se taire sur ce qu'il ignore — donnait au décodage contraint de Gemini la permission de se taire **par défaut** : un aliment revenait sans glucides, sans lipides et sans fibres. Exiger la clé tout en autorisant `null` dit ce qu'on voulait dire ; se taire sur un aliment **entier** reste possible, et c'est le prompt qui le porte.

Substance du prompt système :

> - Tu identifies les aliments et boissons visibles, ainsi que leur quantité estimée.
> - Tu réponds uniquement par un tableau JSON conforme au schéma fourni.
> - Un aliment composé est décomposé en ingrédients principaux lorsque c'est possible (« salade César » → laitue, poulet, parmesan, croûtons, sauce).
> - Tu utilises l'unité la plus naturelle : grammes pour les solides, millilitres pour les liquides, `PIECE` pour les éléments dénombrables.
> - Tu n'inventes pas d'aliment non visible et tu ne fournis aucune valeur nutritionnelle.
> - `confidence` reflète ta certitude sur l'identification **et** sur la quantité.
> - Les libellés sont en français, au singulier, sans marque.

~~Réglages : `temperature = 0.2`, `max_tokens = 1024`. Pas de raisonnement demandé.~~ **Les trois sont tombés au contact de l'API** ([D76](11-decisions.md#d76--trois-prescriptions-de-docs05-tombent-au-contact-de-lapi-et-le-raisonnement-reste-actif---validée)) :

- **`temperature` est retirée** des modèles Claude actuels, avec `top_p` et `top_k` : les envoyer rend un `400`. La régularité qu'on cherchait par là vient maintenant du schéma de sortie, qui contraint la forme.
- **Le raisonnement est actif par défaut**, et le levier recommandé pour dépenser moins est de baisser l'effort, pas de le couper : couper traîne deux modes d'échec documentés — un appel structuré rendu en texte brut, des balises de raisonnement dans la réponse visible — pour une économie que l'effort donne sans risque. Il est donc réglé au plus bas, et le raisonnement reste actif.
- **`max_tokens` plafonne le raisonnement *et* la réponse ensemble.** 1 024 tronquerait le JSON en silence ; la valeur est large.

Le schéma JSON est envoyé au modèle quand le fournisseur le permet, et rappelé dans le prompt sinon.

### Robustesse du parsing

Même avec une sortie structurée, un modèle finit par renvoyer du JSON entouré de texte ou tronqué. Le parseur commun applique, dans l'ordre :

1. extraction du premier bloc `[...]` ou `{...}` équilibré **qui se décode** ;
2. décodage tolérant (`ignoreUnknownKeys`, `coerceInputValues`, `isLenient`) ;
3. validation métier : quantité > 0, libellé non vide, unité connue (sinon `PIECE`), confiance ramenée dans `[0, 1]` ;
4. en cas d'échec total, `AiError.Unparseable` — et l'interface propose **Réessayer** ou la saisie manuelle. Jamais de plantage, jamais de liste vide silencieuse.

**« Qui se décode » n'est pas une nuance.** Une phrase d'introduction qui contient une accolade — *« voici l'analyse (format {label, quantité}) : [...] »* — détournerait la lecture vers quelque chose qui n'est pas du JSON, et une réponse parfaitement valide serait déclarée illisible. Les blocs sont donc essayés dans l'ordre jusqu'au premier qui rend un tableau.

**Le retrait des clôtures Markdown a disparu de la liste** : il ne servait à rien. Une extraction par blocs équilibrés ignore déjà tout ce qui entoure le JSON, y compris trois accents graves.

**Une réponse lisible mais vide n'est pas un échec de parsing** : elle rend `AiError.NothingRecognized`, distinct d'`Unparseable`. Les deux n'invitent pas au même geste — l'une se réessaie telle quelle, l'autre demande une meilleure photo.

Les délimiteurs à l'intérieur d'une chaîne ne comptent pas, ni ceux qu'un antislash échappe : un libellé contenant un crochet solitaire couperait sinon le tableau en deux.

Une ligne mal formée est **écartée seule** ; elle n'emporte pas les autres. Une assiette de six aliments dont un illisible vaut mieux qu'un échec complet.

## Analyse approfondie

Une case à cocher dans les réglages, **éteinte par défaut** : *plus lent, mais plus précis — le modèle échange avec l'application*. Elle ne change rien à ce qui est envoyé de votre repas ; elle change qui décide de la fiche retenue ([D109](11-decisions.md#d109--le-modèle-choisit-la-fiche-parce-quil-en-sait-plus-que-notre-score---validée)).

### Deux outils, et la réponse passe par l'un d'eux

| Outil | Ce qu'il fait |
|---|---|
| `chercher_aliments` | Prend des libellés, rend jusqu'à six fiches par libellé — voir [04](04-sources-de-donnees.md#le-catalogue-outillé--quand-le-modèle-choisit-lui-même) |
| `rendre_le_repas` | Rend le repas analysé, chaque ligne portant `reference` si une fiche convient |

**La réponse passe par un outil elle aussi, et ce n'est pas un détour.** Le chemin ordinaire force la sortie par un schéma — `output_config.format` chez Anthropic, `responseSchema` chez Gemini. Rien dans la documentation des deux ne dit si ce forçage **se combine** avec un appel d'outil. En mode approfondi il n'y a donc aucun forçage : le JSON arrive dans les arguments de `rendre_le_repas`, et c'est le parseur commun qui le lit — il ne sait pas d'où vient la chaîne.

**Un seul appel d'outil par tour** est demandé aux deux fournisseurs. Un tour qui en rendrait trois obligerait à répondre aux trois dans un unique message, et la moindre erreur y apprendrait au modèle à cesser d'appeler en parallèle.

### Le tour du modèle se rejoue tel quel

**Ce que le modèle a envoyé repart intact, jamais reconstruit** ([D110](11-decisions.md#d110--le-tour-du-modèle-se-rejoue-tel-quel-jamais-reconstruit---validée)). Les deux fournisseurs l'exigent : Gemini attache à ses appels d'outil une **signature de pensée**, Anthropic une signature sur ses blocs de raisonnement, et rejouer un tour sans elles rend un `400`.

Reconstruire le tour depuis nos types reviendrait à promettre qu'on connaît tous les champs du fournisseur — c'est faux, et ça l'est resté le temps d'une livraison. Le contenu venu du modèle voyage donc en **JSON brut** : on le décode pour lire l'appel, jamais pour le renvoyer. Seuls les contenus qu'on fabrique passent par un type.

### Trois tours, puis on conclut

Trois recherches au maximum, plus un tour pour conclure — quatre requêtes. Un seul aller-retour ne laisserait aucune occasion de se rattraper : « merguez grillée » ne trouve rien là où « saucisse de bœuf » trouve.

**L'analyse ordinaire reste le filet.** Une boucle a plus de façons d'échouer qu'un aller-retour — un modèle qui répond en texte, trois tours sans conclure, un fournisseur qui refuse le champ des outils — et aucune ne justifie de laisser l'utilisateur bredouille alors que le chemin ordinaire marche. Trois pannes ne se retentent pas : réseau absent, clé refusée, quota épuisé.

### Qui sait le faire

Seuls les fournisseurs marqués comme sachant appeler des outils — Anthropic et Gemini à ce jour. Chez les autres, la case se **grise sans s'éteindre** : le réglage reste et reprendra effet dès qu'un fournisseur capable redevient actif.

Les deux dialectes ne se ressemblent pas et **aucun n'a été deviné** : chez Gemini les outils sont enveloppés dans `functionDeclarations`, l'appel arrive dans une *part* `functionCall`, et sa réponse repart dans une part `functionResponse` dont le champ `response` est un **objet** — là où Anthropic attend une chaîne.

## Sécurité des clés

Les clés API sont la donnée la plus sensible de l'application : elles engagent l'argent de l'utilisateur.

- **Stockage** : ~~`EncryptedSharedPreferences`~~ **le Keystore d'Android en direct** — une clé `AES256-GCM` générée dans le trousseau, adossée au matériel quand l'appareil le permet, qui chiffre la clé d'API ; le chiffré va dans des préférences ordinaires. `androidx.security:security-crypto` est **dépréciée** depuis juin 2025 et son avis renvoie à cet usage ([D77](11-decisions.md#d77--la-clé-va-dans-le-keystore-en-direct-et-le-bouton-tester-est-une-vraie-analyse---validée)). **Seule la clé est chiffrée** : le modèle et l'URL n'en sont pas. Un chiffré que le trousseau ne sait plus ouvrir — appareil changé, verrou retiré — se lit comme « aucune clé », jamais comme une clé vide.
- **Jamais journalisée.** Un intercepteur OkHttp de redaction masque tout en-tête `Authorization`, `x-api-key`, `x-goog-api-key`. Les journaux réseau détaillés sont compilés dans la variante `debug` uniquement.
- **Jamais sauvegardée.** Ni dans le fichier Drive, ni dans l'export local, ni dans la sauvegarde système Android (`android:allowBackup="false"` sur le fichier de préférences chiffré, et règles `data_extraction_rules.xml` explicites).
- **Jamais affichée en clair.** Champ masqué, révélation temporaire à la demande.
- **Aucun intermédiaire.** L'appel part du téléphone vers le fournisseur. Le projet n'a pas de serveur, donc pas d'endroit où une clé pourrait fuiter.

Un bouton **Tester** exécute une requête minimale, confirme la validité et détecte la capacité vision, avant tout usage réel. **C'est une vraie reconnaissance** — même prompt, même schéma, même parseur — et non un appel allégé écrit pour l'occasion : un appel spécial pourrait réussir là où l'analyse échoue, et un bouton qui dit oui à tort est pire que pas de bouton. Il éprouve **le formulaire** et non ce qui est enregistré, faute de quoi il faudrait écrire une clé fausse pour découvrir qu'elle est fausse.

## Coût

L'utilisateur paie ses appels : il a le droit de savoir combien.

Un compteur local par fournisseur enregistre nombre d'appels, tokens d'entrée et de sortie (quand l'API les renvoie). ~~Et une estimation en euros à partir d'une table de tarifs embarquée, datée et signalée comme indicative.~~

**Le mode debug montre les corps** ([D108](11-decisions.md#d108--le-mode-debug-montre-les-corps-et-nécrit-rien-nulle-part---validée)). Le journal réseau existant décrit la requête — méthode, URL, en-têtes masqués — et jamais son corps, qui est pourtant ce qui explique une réponse inattendue. L'intercepteur de mise au point fait l'inverse : les corps, et **aucun en-tête du tout**. Une liste d'en-têtes secrets se complète après avoir été oubliée ; un corps ne porte pas de clé. Rien n'est écrit sur le disque.

**L'estimation disparaît** ([D106](11-decisions.md#d106--une-clé-sobtient-quelque-part-et-les-barres-du-haut-passaient-sous-lhorloge---validée)). La date et l'avertissement étaient là, et cela ne suffit pas : un prix relevé un jour donné vieillit sans prévenir, personne ne le corrige, et un montant approximatif affiché avec l'autorité d'un chiffre est pire qu'aucun montant. Le fournisseur facture exactement, et c'est chez lui qu'on lit sa facture.

Réduction du coût par construction :

- image redimensionnée à 1024 px et compressée en JPEG 80 (≈ 150 Ko, ≈ 250 à 400 tokens selon le fournisseur) ;
- une seule image par requête ;
- pas d'historique de conversation : chaque analyse est indépendante — **sauf en analyse approfondie**, où chaque tour renvoie toute la conversation, l'assiette comprise, donc le quatrième se paie quatre fois , et le compteur en fait la somme — un seul tour muet rendant le total inconnu plutôt que partiel ;
- le repli d'estimation des macros est **groupé** en un appel pour toutes les lignes non résolues, jamais un appel par ligne.

## Confidentialité

Le mode photo envoie une image de votre repas à un tiers. C'est inévitable et l'application le dit clairement, une fois, avant la première utilisation :

> *Votre photo part chez **Google Gemini**, avec votre clé API. Hexavore n'a aucun serveur : rien ne passe par nous. Ce que Google Gemini en garde, et pour combien de temps, relève de ses conditions.*

L'écran renvoie vers la politique du fournisseur sélectionné et n'affirme rien à sa place.

L'image en route vers le modèle est écrite dans `cacheDir`, jamais dans `MediaStore`, et supprimée dans un bloc `finally` : succès, échec ou annulation. Un nettoyage au démarrage balaie les résidus d'un processus tué en cours de route.

**Ce qui reste, en revanche, est une copie dans `filesDir`**, gardée avec le plat si l'utilisateur le valide ([D127](11-decisions.md)). Elle ne part nulle part, s'efface d'un geste sur l'écran de validation, et un réglage permet de n'en garder aucune. La distinction est celle que [01](01-perimetre.md#contraintes-fermes) a fini par faire : ce qui quitte l'appareil ne le quitte que sur un geste, ce qui y reste appartient à celui qui l'a pris.

## Limites assumées

L'estimation par photo est **approximative**, et le dire clairement vaut mieux que de laisser l'utilisateur le découvrir.

- Un modèle voit mal les quantités sans référence d'échelle : d'où le champ de contexte facultatif, qui améliore nettement le résultat.
- Ce qui est caché sous la surface (huile de cuisson, sucre dans une sauce, beurre dans une purée) est systématiquement sous-estimé.
- Les plats régionaux hors des cuisines dominantes sont moins bien identifiés.

Traduction dans l'interface : la confiance de chaque ligne est visible, l'écran de validation est obligatoire, et tout est éditable. L'IA fait gagner du temps ; elle ne fait pas autorité.

## Erreurs

Une hiérarchie fermée, traduite en messages compréhensibles. Le code HTTP ne remonte jamais jusqu'à l'écran.

```kotlin
sealed interface AiError {
    data object NoProviderConfigured : AiError
    data object InvalidKey : AiError          // 401, 403
    data object QuotaExceeded : AiError       // 429, crédits épuisés
    data object NoNetwork : AiError
    data object Timeout : AiError             // 60 s
    data object VisionUnsupported : AiError
    data object Unparseable : AiError
    data object NothingRecognized : AiError   // ajouté en D72
    data class  Server(val status: Int) : AiError
}
```

Chaque cas a un message, et la plupart ont une action : ouvrir les réglages, réessayer, basculer en saisie manuelle. Un message d'erreur sans issue est un bug d'ergonomie.
